You are going to send a file and watch it arrive. The quickest way to see it work is to send to
yourself, in two tabs, so nothing depends on anyone else being ready.

<Steps>
  <Step title="Open Rilldrop and pick a file">
    Go to [localhost:3000](http://localhost:3000) and drop a file onto the card, or click it to browse.
  </Step>
  <Step title="Create the link">
    Click **Create secure link**. Rilldrop shows a link, a **Copy** button, and **Show QR**.
  </Step>
  <Step title="Open the link in a second tab">
    Paste it into a new tab. In real use this is where you would send the link to someone, or
    have them scan the QR code with their phone.
  </Step>
  <Step title="Watch it arrive">
    The transfer starts on its own after a couple of seconds. When the file lands, a download
    button appears on its row in the second tab. Click it to save.
  </Step>
</Steps>

## What just happened

Your two tabs found each other through Rilldrop's signaling server and then connected **directly**.
The file went from one to the other without passing through any server, which is why there is no
size limit and no upload to wait for.

The badge at the top of the card said **Direct** once that path was open. On a network that
blocks direct connections it would have said **Relay** instead, and the file would have traveled
through an encrypted relay that cannot read it. See [How Rilldrop connects](/how-it-works/signaling).

## The same thing from the desktop app or the terminal

Both do everything the browser does, plus folders, plus writing straight to disk.

<CodeGroup>
```bash CLI
# install (macOS)
curl -fsSL https://raw.githubusercontent.com/Arnavsharma2/rilldrop/main/client/public/install.sh | sh

rilldrop send photo.jpg
# prints a three-word code and a link; share either
```

```powershell Desktop
# build or download Rilldrop Desktop from GitHub Releases,
# then drop files on the window, click Send,
# and share the room code, the link, or the QR
```
</CodeGroup>

The receiving side is `rilldrop receive olive-tiger-castle`, or pasting the same code or link into
Rilldrop Desktop's **Receive** tab.

## Any Rilldrop can talk to any other {#cross-platform-transfers}

The browser speaks to the signaling server one way and the desktop app and CLI another, but they
all land in the same room, so every pairing works in both directions.

| Sender | Receiver | How the receiver joins |
|--------|----------|------------------------|
| Browser | Browser | Opens the link or scans the QR code |
| Browser | Desktop | Pastes the link into the Receive tab |
| Browser | CLI | `rilldrop receive "<link>"` |
| Desktop | Browser | Opens the link or scans the QR code |
| Desktop | Desktop | Pastes the code or the link into the Receive tab |
| Desktop | CLI | `rilldrop receive <code>` or `rilldrop receive "<link>"` |
| CLI | Browser | Opens the link or scans the QR code |
| CLI | Desktop | Pastes the code or the link into the Receive tab |
| CLI | CLI | `rilldrop receive <code>` or `rilldrop receive "<link>"` |

One asymmetry is worth remembering. **A browser recipient always needs the link.** The web app has
no field for a three-word code, and a browser sender never mints one. Codes come from `rilldrop send`
and Rilldrop Desktop, and both of those also accept a link. When you do not know what the other person
will use, share the link.

Folders are the other difference: the CLI and the desktop app send them and rebuild the structure
on arrival, and the browser cannot send them at all. A browser recipient of a folder can still get
the structure back by choosing **Download ZIP**, which rebuilds it inside the archive; saving files
one at a time flattens them.
